# Online PvP kickoff disconnect — network primary-source research

Saved 2026-09-08 (Europe/Istanbul). An early checkpoint was saved before the completed research. No launcher, game, or game-service endpoint was contacted; no network probe or configuration change was made.

## Finding

The strongest network interpretation is a failure when the session changes from account/matchmaking traffic to the PvP gameplay path. The reported control is unusually useful: online AI play works, but play against another person disconnects exactly at kickoff in both FIFA 17/Reborn17 and FIFA 15/Aurora15. That makes a general login, DNS, account, or server-reachability failure less likely. It does **not** by itself prove that either specific match used direct peer-to-peer UDP; no packet capture or project transport specification is available.

Static evidence nevertheless makes a gameplay UDP/P2P hypothesis concrete:

## Ranked, falsifiable hypotheses

| Rank | Hypothesis and confidence | Why it fits | Evidence that would falsify it |
|---:|---|---|---|
| 1 | **The inbound PvP UDP path is blocked at the macOS/CrossOver boundary.** Untested; first network branch. | Both Windows launchers assume a Windows host. Aurora explicitly tries to create an inbound UDP Windows Firewall rule. Apple's application firewall can deny incoming attempts until an app is allowed. A Windows-side rule does not demonstrate that the macOS host process is allowed. Online AI does not require a remote peer to initiate packets to the local gameplay socket. | At kickoff, packet/socket tracing shows remote UDP datagrams reaching the correct Wine socket and the game consuming them, or the same Mac succeeds in PvP without any firewall-state difference. |
| 2 | **A CrossOver Winsock compatibility difference breaks the gameplay handoff or socket setup.** Untested. | The common factor is two old Windows games under the same compatibility layer, while login/AI paths work. Current upstream Wine supports IPv4/IPv6 datagram providers and routing queries, but `WSAGetQOSByName` is a stub and unhandled `WSAIoctl` codes, including `SIO_SET_QOS`, return `WSAEOPNOTSUPP`. Microsoft specifies that `SIO_SET_QOS` associates QoS with a socket and permits `WSAENOPROTOOPT` when unsupported. This is a test target, not evidence that either FIFA calls it or that CrossOver 26.3 matches current Wine master exactly. | A kickoff trace contains no failing/unimplemented Winsock operation, or native Windows fails in the same endpoint/match pattern. A logged unsupported call that the game ignores also falsifies it as causal. |
| 3 | **The current Internet edge has UDP NAT/filtering or UPnP mapping behavior incompatible with peer establishment.** Untested. | Both exact games contain UPnP and P2P vocabulary. RFC 4787 explains why endpoint-dependent UDP mappings/filtering can break peer applications and force relay use. Successful HTTPS/login/matchmaking does not test the router's inbound UDP mapping behavior. | Both native Windows and CrossOver succeed/fail identically on two independently routed endpoints, or capture proves bidirectional gameplay UDP survives the NAT while the disconnect still occurs. |
| 4 | **The game advertises or binds the wrong IPv4/interface under Wine.** Untested. | Aurora explicitly requires an IPv4 GameHost and contains IPv4 resolution code. Wine's published source shows address-list and best-route emulation; the latter rejects non-IPv4 destinations in current master. A VPN, virtual adapter, stale Wi-Fi/Ethernet address, or different adapter order could therefore affect only the peer path. | With one active physical interface, the local address advertised to the opponent matches the socket's bound/routed address and packets are bidirectional; or native Windows advertises the same address and fails identically. |
| 5 | **Relay selection/reachability is broken for this client or region.** Untested. | Aurora's binary explicitly names relay fallback, and Reborn embeds two European relay labels. A direct attempt may fail and the relay fallback may be unreachable, malformed under Wine, or not selected. The two projects' different services make a simultaneous general outage less likely, but do not exclude a shared client incompatibility. | A failing match is captured as direct peer traffic with no relay attempt expected, or the same selected relay succeeds from CrossOver in another PvP match. Native Windows failing against the same relay on both endpoints points toward project service state instead of CrossOver. |

QoS congestion is not ranked separately. EA's current guidance describes router QoS as bandwidth prioritization for packet loss/jitter; it does not support QoS as a likely cause of a deterministic transport switch at kickoff. The relevant CrossOver question is narrower: whether a required Winsock QoS call fails and the game treats that failure as fatal.

## Discriminating test sequence for a later live session

Run one controlled matrix before changing ports or router settings. Use the same launcher builds, game builds, account, game mode, region, and preferably the same opponent. Endpoint A is the current connection. Endpoint B must be a different ISP/router; a second fixed broadband line with public IPv4 and working UPnP is a stronger control than a cellular hotspot, which may itself use carrier-grade NAT.

| Test | CrossOver/macOS | Native Windows control | Result meaning |
|---|---|---|---|
| Endpoint A, one FIFA at a time | One online-AI match, then one PvP match | Same sequence in the same 30-minute window | Windows passes PvP while Mac fails: prioritize ranks 1, 2, and 4. Both fail: endpoint/project/peer remains plausible. |
| Endpoint B, same sequence | Repeat without changing launcher/game settings | Repeat on the same Endpoint B | Both OSes fail A and pass B: rank 3. Mac fails A+B while Windows passes A+B: CrossOver/macOS path. One project fails on both OSes/endpoints: project-specific path. |

Then collect a short, header-focused trace around a single failed kickoff, recording both clocks and their offset. A limited snapshot can still contain partial payload:

1. On macOS, record the interface list/default route, active VPN/virtual adapters, macOS application-firewall state and allowed-app list, and Wine UDP sockets before matchmaking and for 30 seconds after kickoff. Capture a limited snapshot around the observed TCP/UDP/ICMP flows during that window; do not guess a gameplay port. Snapshot length does not guarantee zero payload collection.
2. Correlate each socket's local address/port with outbound and inbound packets. “Outbound only” after opponent assignment raises firewall/NAT/relay reachability as a branch only after process survival and capture coverage are established; packets arriving at the Mac interface but not the socket raise host filtering or Wine delivery as candidates.
3. Only if the observed firewall state and incoming-flow evidence justify it, repeat once with an explicit macOS firewall allow entry for the actual CrossOver-FIFA/Wine receiving process, preserving the previous state for rollback. A pass after only this change supports rank 1. Do not disable the whole firewall as the first test.
4. Capture a CrossOver `winsock` trace for the same short window. Search for `WSAGetQOSByName`, `SIO_SET_QOS`, routing/interface queries, `WSAEOPNOTSUPP`, bind failures, and UDP send/receive errors. A repeated failure at the handoff, absent on Windows, supports rank 2; mere presence of a stub warning does not.
5. If rank 3 or 5 remains, inspect the router's UPnP/NAT mapping table during the attempt and classify each flow by destination: opponent, project server, or relay, using launcher logs/capture evidence. Compare Endpoint A/B and Windows/macOS. Do not create manual forwards until the actual local port and flow direction are observed.

The result grid should record pass/fail, exact disconnect time, opponent, online-AI control result, active interface, local/private IPv4, whether a public IPv4 is assigned to the router, UDP socket tuple, inbound/outbound packet counts, relay evidence, and the first socket error. Redact account tokens and packet payloads.

## Evidence limits

- No public source repository, protocol document, port list, or topology description was discoverable for Reborn17 3.1.10 or Aurora15 Connector 1.1.51 on 2026-09-08. Their embedded project origins did not expose indexed documentation. The project identity above is therefore verified from the exact artifacts' self-description and hashes, not an independent signed release manifest.
- “Lobby/control traffic differs from PvP gameplay traffic” is an inference from the symptom plus static capabilities. No trace proves whether login/matchmaking is TCP/HTTPS, whether gameplay is direct P2P UDP, when relay fallback happens, or who initiates the first gameplay packet.
- No exact gameplay port is asserted. Aurora's extracted firewall-rule label is truncated. EA's historical retail port lists would also not prove the ports used by either unofficial service.
- Current Wine master is a primary implementation reference, but it is not the exact CrossOver 26.3 source snapshot. CodeWeavers says CrossOver 26 includes Wine 11.0 and offers FOSS source for 26.3.0; the exact `ws2_32` implementation was not downloaded or built in this no-change research pass.
- The existing September 5 diagnostic archive is for Aurora17, not either supplied launcher, and predates this PvP symptom report. It cannot establish the transport or cause.
